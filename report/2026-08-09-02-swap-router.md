**Date:** 2026-08-09
**Scope:** `contracts/swap/router/SwapRouterV1.sol`, `contracts/swap/router/ISwapRouterV1.sol`, `contracts/swap/general/ISwapBridgeV1.sol` (context), `contracts/swap/morpho/SwapBridgeMorphoV1.sol` (context)

## Update — 2026-08-09

- **M-01 is RESOLVED.** `SwapRouterV1` now has a curator-gated `sweep(IERC20 token, address to, uint256 amount)` (`stable.verifyCurator(msg.sender)`, matching `RewardRouterV0.setApprove`'s convention), emitting a `Sweep` event. Any balance stranded in the router — via a mis-set `target`, a stray direct transfer, or dust left behind by L-01 below — can now be recovered by the curator to its rightful owner. The optional hardening this finding also suggested (rejecting `target == address(this)` in `_swapIn`/`_swapOut` to close the self-inflicted case outright) was not added; `sweep()` alone is a sufficient recovery path.
- **L-01 is unchanged** — not addressed. `sweep()` gives the curator a way to recover a stray balance before it's silently absorbed by an unrelated call, but the underlying cause (allowance left on `coin` to a module that under-consumes) still isn't reset by the router itself.

## Findings

### [M-01] No rescue path for tokens stranded in the router — RESOLVED
**Location:** `contracts/swap/router/SwapRouterV1.sol` (contract-wide — no such function exists)

**Description:**
`SwapRouterV1` is deliberately stateless and permissionless: it holds `coin`/stablecoin only transiently between pulling from the caller and forwarding to the module, and has no owner, curator gate, or admin function of any kind. That means there is no way to recover value in either of these realistic scenarios:

- A caller (or an integrating frontend/wallet with a bug) passes `target = address(router)` to `swapInTo`/`swapOutTo`/`execute`. The module happily mints/sends the output *to the router itself*, where it has no owner and sits permanently.
- A user (or another contract) sends `coin` or stablecoin directly to the router's address by mistake (e.g. copy-pasting the router address instead of a personal wallet) — plain ERC20 `transfer`, not a swap call at all.

Once tokens land in the router's balance this way, they are picked up implicitly on the next unrelated `swapIn`/`swapOut` call to the same token (since `forceApprove`/`safeTransferFrom` operate on the router's pooled balance, not on a per-call reserved amount), but there is no way for the original depositor to reclaim their specific funds, and no `sweep`/`rescue` function exists for a curator or anyone else to return them.

**Recommendation:**
Add a curator-gated `sweep(IERC20 token, address to, uint256 amount)` (mirroring `stable.verifyCurator(msg.sender)` as used elsewhere in this codebase, e.g. `RewardRouterV0.setApprove`) so accidentally-stranded balances can be returned to their rightful owner. Optionally also reject `target == address(this)` in `_swapIn`/`_swapOut` to close off the self-inflicted case outright.

**Fix:** Implemented as recommended — `SwapRouterV1.sweep(IERC20 token, address to, uint256 amount)`, gated by `stable.verifyCurator(msg.sender)`, emits `Sweep(token, to, amount)`. The `target == address(this)` rejection was not added, but is no longer load-bearing now that a recovery path exists.

### [L-01] Lingering ERC20 allowance to a module that under-consumes the pulled amount  *(Low)*
**Location:** `contracts/swap/router/SwapRouterV1.sol:69`

**Description:**
`_swapIn` does:
```solidity
coin.safeTransferFrom(msg.sender, address(this), amount);
coin.forceApprove(address(module), amount);
uint256 amountStable = module.swapInTo(target, amount);
```
`forceApprove` sets the allowance to exactly `amount` and the call assumes `module.swapInTo` fully consumes it via its own `coin.safeTransferFrom(router, module, amount)`. This holds for `SwapBridgeMorphoV1` today, but the whole point of routing via `ISwapBridgeV1` is to let future, differently-implemented modules plug in without router changes. Any future module that pulls less than the full `amount` (partial-fill logic, a bug, or a fee-on-transfer `coin` — see I-01) leaves a residual allowance on `coin` from the router to that module, which the module can later draw down out-of-band against whatever balance the router happens to hold at that time (see M-01 on why the router can hold a stray balance at all).

**Recommendation:**
Reset the allowance to zero after the call (`coin.forceApprove(address(module), 0)`), or check `module.swapInTo` consumed the full amount and revert otherwise. Low severity because it requires either a future non-conforming module or an existing stray balance to be meaningful.

## Notes

- **[I-01] Fee-on-transfer / non-standard `coin` incompatibility.** `_swapIn` approves and forwards the nominal `amount` without checking the router's actual balance delta after `coin.safeTransferFrom(msg.sender, ...)`. A fee-on-transfer `coin` would cause the downstream `module.swapInTo` call to revert (the module would try to pull more than the router actually received). This is inherited from `SwapBridgeMorphoV1`'s own identical assumption, not introduced by the router, but worth flagging since the router is the reusable entrypoint going forward — reasonable to document as a require of any `coin` registered by the curator (no fee-on-transfer, no rebasing) or to add an explicit check.

- **[I-02] No dedicated test suite for `SwapRouterV1`.** `test/swap/` only covers `SwapBridgeMorphoV1` directly; there's no coverage yet for routing through `SwapRouterV1` (single swaps, `execute()` batching, `NotAModule` rejection, or `swapOut` continuing to route to an expired-but-still-registered module). Worth adding before this ships, especially given M-01/L-01 above are exactly the kind of thing a test would surface concretely.

- **[I-03] `execute()` has no per-batch size cap.** `modules`/`targets`/`amounts`/`isSwapIn` are unbounded calldata arrays; a large enough batch simply exceeds the block gas limit and reverts. This only affects the caller of that specific transaction (self-inflicted, not a griefing vector against other users or the contract), so not a finding, just worth knowing if a frontend wants to pre-validate batch size instead of relying on simulation.

- Confirmed by design (not a finding): `_verifyModule` intentionally uses `stable.checkModule()` rather than `stable.checkValidModule()`, so `swapOut`/`swapOutTo`/`execute` keep routing to a module even after it has expired — this matches `SwapBridgeMorphoV1.swapOutTo`'s own documented post-expiry behavior. `swapIn` to an expired module still safely reverts, enforced independently inside the module via `Stablecoin.mintModule`'s `validModule` modifier (checked against the module's own address, not the router's), so the router doesn't need to duplicate that check.
